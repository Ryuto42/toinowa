## 今回用意するもの：実物の紙3枚、合計9ファイル

手元の模試結果から、下のA・B・Cを1ページずつ選ぶ。3人分や3回分である必要はない。目的は成績の個人差ではなく、書式と情報の種類の違いを含めること。

| 紙 | 選び方 | 確認したいこと |
| --- | --- | --- |
| A | 科目・得点・満点・偏差値が並ぶ全体成績のページ | 基本の数値と科目の対応 |
| B | Aとは表の並びや書式が違う全体成績のページ。可能なら別の模試会社 | 特定の書式に依存していないか |
| C | 設問別・単元別結果、正答率、弱点などが載ったページ | 細かな表、割合、単元名の対応 |

CはAまたはBと同じ模試の別ページでよい。同じ書式しかなければBは別の回の結果でもよいが、書式の多様性が少ない点を報告する。最初から大量に集めない。

各ページについて、以下の3ファイルを作る。**1ファイルに1ページ、A・B・Cを別々に保存する。**

| 条件 | 方法 | ファイル名 |
| --- | --- | --- |
| スキャンPDF | Adobe Scan等で平らな紙を鮮明に取り込む。各1ページで保存 | A_scan.pdf、B_scan.pdf、C_scan.pdf |
| 通常写真 | スマホの通常カメラで明るい場所から正面に撮る。四隅を入れ、紙を画面いっぱいにする | A_clear.jpg、B_clear.jpg、C_clear.jpg |
| 影のある写真 | 通常写真と同程度の距離・向きを保ち、一部に軽い影がかかる状態で撮る。暗すぎたりピンぼけにしたりしない | A_shadow.jpg、B_shadow.jpg、C_shadow.jpg |

写真はJPEGまたはPNGでよく、PNGへ変換する必要はない。iPhone等でHEICになる場合はJPEG/PNGへ書き出す。自分で縮小・圧縮せず、元の大きさで渡す。1ファイル15MB以内。スキャンPDFと通常写真の違いには補正なども含まれるため、形式だけの効果とは解釈しない。

氏名・学校名・受験番号・QR/バーコードなどは、撮影前に不透明な紙で隠す。同じ隠し方を3条件で揃え、科目・点数・単元名を隠さない。結果の集計を発表し、実物資料そのものの公開は別途扱う。

### 既に渡された架空PDFの扱い

`模試個人成績表_山田テスト_改訂版.pdf` は受領済み。A4横2ページ、一部の文字が約4〜5ptと小さいため「細字・高密度の追加難例」として元PDFのまま使う。今回の準備では印刷・撮影も、読みやすい別版の作成も不要。実物9条件の主評価と架空PDFの結果は混ぜず、別表にする。Webスクリーンショットも今回は不要。

## 渡し方と、その後の手順

1. 上記9ファイルを同じフォルダへ入れる。`benchmark-data/exams/`（Git対象外）でも、別のローカルフォルダでもよい。
2. フォルダのパスを伝えるか、ZIPまたは9ファイルを添付する。写真の撮影条件がファイル名から分かれば追加メモは不要。
3. `.env.benchmark.local` に本人の実験用APIキーを保存する。実験上限2ドルは設定済み。キーはチャットに貼らない。
4. エージェントが画質・匿名化・ファイル対応を確認する。スキャンPDFと通常写真から科目・点数・偏差値・単元別結果の正解表を作り、本人が手元の紙と照合する。CSVやJSONの準備は不要。
5. 正解と評価対象の項目を固定した後、OrcaReplayで画像付き入力の保持と費用記録を1件で確認し、3モデルを同条件で比較する。うまく接続できなければ、同じ入力・設定でOrcaRouterを直接呼ぶ比較方式に切り替える。
6. 予算内で主評価を実施し、モデル別・撮影条件別の表、読み違いの実例、推奨モデルと根拠を提出する。

正解表は各ページの全科目・点数・満点・偏差値と、Cの単元別数値を対象にする。元資料で「正答率」が本人の得点率なのか受験者全体の正答率なのか不明なら意味を推測せず、見出しと値の転記として採点する。グラフから推定する数値は、明示された数値と分ける。

この9ファイルは3枚の紙の撮影条件違いであり、「独立した9枚の成績表」とは数えない。少数資料による予備検証として報告する。

## アカウントと費用

サービス本体の `.env.local` は変更しない。本人のクレジットがあるワークスペースで実験用の通常APIキーを発行し、`.env.benchmark.local` の `BENCHMARK_ORCAROUTER_API_KEY` に保存する。チャットには貼らない。単にキーを新しくするだけでは請求先は変わらず、所属ワークスペースの確認が必要。

`BENCHMARK_MAX_COST_USD=2` を本人の回答に基づいて設定済み。キー単位のspending capも利用可能なら設定する。費用不明を0ドルとして扱わない。アプリ側だけの事後合計では実行中1リクエスト分の超過を完全には防げないため、事業者側上限と併用する。失敗・再試行の課金も集計する。

## OrcaReplayを優先する方法

公式資料で確認済み: セッションを記録し、特定のモデル呼び出しを他モデルで再実行して、出力・レイテンシ・費用を比較できる。CLIは `orca compare`、記録済みの応答をオフラインで再生するだけの `orca replay` とは別物。比較で新たにモデルを呼ぶ場合は課金される。

今回の検証: 0.4.0の `record generic-openai` と `compare --from 1 --models ...` を利用。元の画像ファイルを再読込するワーカーを毎回起動し、同じJSONを送る。ローカル上流スタブで、3候補とも送信ペイロードがモデル名以外完全一致することを確認。保存トレース内のbase64は高エントロピー情報として一部マスクされるため、トレースだけから元画像を再構成しない。元画像・リクエストのハッシュは別のGit対象外ディレクトリに保管する。

ゲートウェイとの記録同期に使うreplayスコープのキーはモデル呼び出し用キーとは用途が違う。最初から追加キーを求めず、利用方法が決まった後に必要なものだけ設定する。CLI使用時は実験用の最小フォルダで記録し、サービスのDB書き込みやファイル変更を再実行しない。

## 比較条件

候補: `google/gemini-2.5-flash`、`openai/gpt-4o-mini`、低コスト対照として `google/gemini-2.5-flash-lite`。本人のモデル一覧で画像入力の利用可否を確認する。

1. アプリの `src/components/document-reader.tsx` と同じ前処理を使用する。写真は長辺1600px以下、PDFは各ページを長辺1600px以下かつ最大2倍で描画し、JPEG品質0.85に変換。合計3.5MBの制約も揃える。
2. 模試登録の `src/lib/jobs/exam-handler.ts` のプロンプト、`examAnalysisResultSchema`、構造化出力、max_tokens=6000を揃える。別のOCR用プロンプトだけで評価しない。
3. 単体比較では要求モデルを固定。代替モデルに切り替わった結果を元モデルの点数へ混ぜない。要求モデルと実使用モデルを双方記録する。サービスの再試行・フォールバック込みの比較は別枠にする。
4. まずA_scan.pdfを3モデルで1回ずつ試し、画像保持・出力・費用・実使用モデルを確認する。比較条件に変更がなければ、この3回を本試験にも含める。主評価は実物9ファイル×3モデル＝27回を基本とするが、2ドル以内で実行できるか初回の費用とモデル料金で判断し、予算を優先する。収まらなければ3枚のスキャンPDF×3モデルの9回を先に揃え、追加する条件を全モデルで揃える。予算不足の途中結果を完全な比較と表現しない。
5. 主評価を優先し、余裕があれば受領済みの架空PDFを3モデルで追加評価する。さらに余裕があれば、結果を見て都合のよい例を選ばないよう、あらかじめ選んだA_scanとC_shadowを各モデルで計3回になるまで再実行し、ばらつきを確認する。オフラインの録画再生は独立した再実行には数えない。順序・実施日時・アプリのコード版・入力とプロンプトのハッシュを残す。
6. 正解表と照合して採点。同じPDFから作った写真は独立した別の模試とは数えず、「書式数」と「入力条件数」を分けて報告する。

## 実施時の補足

最初のFlash-Lite呼び出しは、アプリの1試行15秒に合わせてタイムアウト。失敗記録・費用未確定として保持した。精度評価の主比較27回と再現性確認12回は、全モデル共通で60秒の期限に揃え、15秒以内に返った割合を別途報告する。再試行・フォールバック・JSON修復を無効にした単体モデル試験であり、サービス全体の成功率ではない。事前選定したA_scanとC_shadowを各モデル計3回実行。架空PDFの追加試験は今回は実施せず、実物の再現性確認を優先した。

## 選定の判断方法

- 主評価は実物の重要項目の転記精度。数値の作り足し、科目間の取り違えを特に確認する。得点・満点・偏差値・単元別結果は項目別にも集計する。
- 細かな項目が多いCだけで結論が決まらないよう、ページ別・条件別の成績と全体値を併記する。意味のある差が見えない場合は「この資料では同等」とする。
- JSONエラーやタイムアウトは成功例から除外して隠さず、全要求に対する完了率と費用へ含める。
- 精度が同程度なら、処理時間と実測費用を比較して選ぶ。読めない数値を不明とすることは誤った数値を断定することと区別する。
- 目標・学習時間などの提案は唯一の正解がないため、転記正答率に混ぜず、元資料にない希望の捏造や根拠の有無を別に確認する。
- モデルだけでなく、現在の長辺1600pxという前処理が細字を潰していないかも確認する。前処理やプロンプトを改善した場合は、変更前後を別の実験として扱う。

## 成果物

- 機械可読な実測記録（JSON/CSV）と、出力原文・エラー・再試行の記録
- モデル別・入力条件別の比較表: 重要項目正答率、結果表全体の完全一致率、読めない数値を推測した件数、JSON適合率、完了率、平均・中央値の時間、実測費用と費用未確定の件数
- 科目と点数の対応まで採点する。単に同じ数字が出現しただけでは正解にしない。欠落も失点として扱う
- 学習目標・苦手範囲・学習時間の提案は転記精度と分離し、根拠・捏造・過剰な断定を人が確認
- 実測に基づく推奨モデル、代替モデル、選定理由、弱点と標本数の限界
- OrcaReplayの比較記録・エクスポートと、ハッカソン発表用の短い説明

比較ツールが正解表を自動で知っているわけではない。精度評価は別途定義した正解と照合する。少数の架空資料での結果を、全模試での一般的な性能と表現しない。
