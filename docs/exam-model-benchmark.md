# 模試読み取りモデルの比較実験

**続きの記録:** 検証・復旧の本体実装と Flash／Pro の比較・採用判断は
[exam-reading-reliability.md](exam-reading-reliability.md)、
途中の追加検証（構造化抽出v2）は [exam-model-benchmark-improvement.md](exam-model-benchmark-improvement.md)。
元の正解表と初回採点はこの文書に残し、追加実験は別記録に分けている。

目的は、費用対効果と信頼性を実測で説明できるモデル選定。
単に最安・平均精度で選ばず、点数・偏差値の取り違え、読めない値の捏造、失敗時の挙動を確認する。

入力は実物の成績表3枚 × 撮影条件3種（スキャンPDF・通常写真・影のある写真）＝9ファイル。
氏名・学校名・受験番号・QR/バーコードは撮影前に隠し、同じ隠し方を3条件で揃えた。
原本・正規化後の画像・正解表はいずれも Git 管理外のローカルディレクトリに置き、リポジトリへ入れない。

## 比較条件

候補: `google/gemini-2.5-flash`、`openai/gpt-4o-mini`、低コスト対照として `google/gemini-2.5-flash-lite`。本人のモデル一覧で画像入力の利用可否を確認する。

1. アプリの `src/components/document-reader.tsx` と同じ前処理を使用する。写真は長辺1600px以下、PDFは各ページを長辺1600px以下かつ最大2倍で描画し、JPEG品質0.85に変換。合計3.5MBの制約も揃える。
2. 模試登録の `src/lib/jobs/exam-handler.ts` のプロンプト、`examAnalysisResultSchema`、構造化出力、max_tokens=6000を揃える。別のOCR用プロンプトだけで評価しない。
3. 単体比較では要求モデルを固定。代替モデルに切り替わった結果を元モデルの点数へ混ぜない。要求モデルと実使用モデルを双方記録する。サービスの再試行・フォールバック込みの比較は別枠にする。
4. まずA_scan.pdfを3モデルで1回ずつ試し、画像保持・出力・費用・実使用モデルを確認する。比較条件に変更がなければ、この3回を本試験にも含める。主評価は実物9ファイル×3モデル＝27回を基本とするが、2ドル以内で実行できるか初回の費用とモデル料金で判断し、予算を優先する。収まらなければ3枚のスキャンPDF×3モデルの9回を先に揃え、追加する条件を全モデルで揃える。予算不足の途中結果を完全な比較と表現しない。
5. 主評価を優先し、余裕があれば受領済みの架空PDFを3モデルで追加評価する。さらに余裕があれば、結果を見て都合のよい例を選ばないよう、あらかじめ選んだA_scanとC_shadowを各モデルで計3回になるまで再実行し、ばらつきを確認する。オフラインの録画再生は独立した再実行には数えない。順序・実施日時・アプリのコード版・入力とプロンプトのハッシュを残す。
6. 正解表と照合して採点。同じPDFから作った写真は独立した別の模試とは数えず、「書式数」と「入力条件数」を分けて報告する。

## 実施方法（OrcaReplay）

公式資料で確認済み: セッションを記録し、特定のモデル呼び出しを他モデルで再実行して、出力・レイテンシ・費用を比較できる。CLIは `orca compare`、記録済みの応答をオフラインで再生するだけの `orca replay` とは別物。比較で新たにモデルを呼ぶ場合は課金される。

今回の検証: 0.4.0の `record generic-openai` と `compare --from 1 --models ...` を利用。元の画像ファイルを再読込するワーカーを毎回起動し、同じJSONを送る。ローカル上流スタブで、3候補とも送信ペイロードがモデル名以外完全一致することを確認。保存トレース内のbase64は高エントロピー情報として一部マスクされるため、トレースだけから元画像を再構成しない。元画像・リクエストのハッシュは別のGit対象外ディレクトリに保管する。

ゲートウェイとの記録同期に使うreplayスコープのキーはモデル呼び出し用キーとは用途が違う。最初から追加キーを求めず、利用方法が決まった後に必要なものだけ設定する。CLI使用時は実験用の最小フォルダで記録し、サービスのDB書き込みやファイル変更を再実行しない。

## 実施時の補足

最初のFlash-Lite呼び出しは、アプリの1試行15秒に合わせてタイムアウト。失敗記録・費用未確定として保持した。精度評価の主比較27回と再現性確認12回は、全モデル共通で60秒の期限に揃え、15秒以内に返った割合を別途報告する。再試行・フォールバック・JSON修復を無効にした単体モデル試験であり、サービス全体の成功率ではない。事前選定したA_scanとC_shadowを各モデル計3回実行。架空PDFの追加試験は今回は実施せず、実物の再現性確認を優先した。

## 選定の判断方法

- 主評価は実物の重要項目の転記精度。数値の作り足し、科目間の取り違えを特に確認する。得点・満点・偏差値・単元別結果は項目別にも集計する。
- 細かな項目が多いCだけで結論が決まらないよう、ページ別・条件別の成績と全体値を併記する。意味のある差が見えない場合は「この資料では同等」とする。
- JSONエラーやタイムアウトは成功例から除外して隠さず、全要求に対する完了率と費用へ含める。
- 精度が同程度なら、処理時間と実測費用を比較して選ぶ。読めない数値を不明とすることは誤った数値を断定することと区別する。
- 目標・学習時間などの提案は唯一の正解がないため、転記正答率に混ぜず、元資料にない希望の捏造や根拠の有無を別に確認する。
- モデルだけでなく、現在の長辺1600pxという前処理が細字を潰していないかも確認する。前処理やプロンプトを改善した場合は、変更前後を別の実験として扱う。

## 結果の読み方

実物2回分の模試、紙3ページ、各3条件の**9入力×3モデル＝27回**が主比較。同じ紙の撮影条件違いを独立した9件の模試とは数えない。加えて事前に選んだA_scan・C_shadowを各モデル計3回になるまで再実行した12回と、最初のタイムアウト試行1回を合わせ、外部API呼び出しは40回。

正解表は結果取得前に作り、利用者が原本と照合して承認済み。回答の `text` をエージェントが科目・設問・列の意味まで照合し、機械集計した。これは人による二重採点ではない。判断と根拠はローカルの採点ファイルで追跡できる。

主指標は**必要項目を、意味も含め正しく取り出せた割合**。Aは実得点・満点・全国偏差値と換算得点の57項目、Bは30項目、Cは設問別得点・配点・全国平均点の63項目。3条件で1モデル450項目。欠落、意味不明、誤り、処理失敗をすべて分母に含める。元資料の空欄4セルは分母から外し、勝手な数値補完を別に確認する。

- 同じ数字が別科目や別列にあっても正解にしない。設問別得点を科目合計として書いたものにも点を与えない。
- 全国平均**点**を「得点率」「％」とした場合は誤り。数字だけで列の意味が判別できない場合は不明確として扱う。
- JSONを取り込めない出力は、その入力の全項目を取得失敗とする。途中まで読めた部分だけを救済しない。
- 学習時間や目標に唯一の正解はないので、数値の転記精度には混ぜない。提案の根拠は別に点検する。

### Flash-Liteが弱い、とだけ結論づけない

集計行・換算得点・平均点を除き、A/Bの単科目の得点・満点・全国偏差値と、Cの設問別得点・配点だけを見る補助集計では、Flash-Liteは**252/252項目一致**。Flashは234/252（JSON失敗による18項目の欠損）、miniは27/252だった。これは結果の内訳を理解するための事後の補助集計で、主指標の置き換えではない。

Flash-Liteの主な問題は、合計行や換算欄の省略、全国平均点の意味、提案の根拠。一方Flashは抽出範囲が広く、項目全体の取得には有利だった。主比較の1件平均費用はFlash約$0.01081、Lite約$0.00064、mini約$0.00441。FlashはLiteの約17倍だが、今回の9件での差額は約$0.0916だった。

## 発見した問題と改善方針

| 発見 | サービスへの影響 | 改善案（この比較では未実装） |
| --- | --- | --- |
| Flash・Liteとも全国平均点を％と読む例 | 苦手単元・優先順位の誤判定 | `score / max / nationalMeanPoints / scoreRate` を別フィールドにし、得点率・平均との差はコードで計算 |
| Liteが合計行・換算欄を省略 | プロフィールの情報不足 | 表ごとの行配列と種別を必須化し、不明はnull。自由文1本への転記をやめる |
| 校内偏差値と都道府県の列の混同 | 同じ数値でも比較対象を誤る | 集団区分を明示したスキーマと、列見出しの根拠を保存 |
| FlashのB_clearで `finish_reason=length` | JSONを登録できない | 画像読取と提案生成を分けて出力を短くする。用途別に推論・出力枠を検証し、上限到達時の再試行を設計 |
| Flashの主比較8/9回が15秒超 | 正しい回答を待たず別モデルへ切り替わり得る | バックグラウンドの模試解析と対話の時間制限を分ける。全体期限・再試行回数・費用上限も併せて調整 |
| miniが順位などを点数として転記 | 誤った学習計画の生成 | 現条件の模試読取では使用しない。HTTP成功だけでフォールバックを受理しない |
| 正しく読めても提案に計算・根拠の誤り | AIがもっともらしい計画を作ってしまう | 抽出事実と学習提案を分離。比較・優先順位の根拠を検算して先生へ提示 |

FlashのJSON失敗では、返却usage上のcompletion 5,986トークンのうちreasoningが5,760、textが226だった。推論が枠を多く使い、文章が途中で終了したことが確認できる。単純に「FlashのOCRは失敗した」とだけ扱わない。

提案の点検でも、FlashのC_clearは「式と証明の得点が全国平均未満」と説明したが、実際には平均を上回っていた。A_scanでは不明なはずの学習習慣を「考慮した」と書く例もあった。Liteは強い科目を弱点として挙げたり、平均点を本人の得点率として提案へ流用したりした。miniは誤転記を根拠に提案し、不確実性を空配列とする例が多かった。**高いモデルを使っても、判断根拠の検証は必要。**

学習時間は主比較の有効な出力で30〜60分の範囲だが、時間の妥当性を実証したわけではない。本人の生活時間ではなく、変更可能な提案として扱う。志望校名の作り足しは確認した主比較出力では見られなかったが、これだけで捏造一般を防げるとは言えない。

## 評価範囲と学習計画への影響についての補足

Aの平均点・順位・校内／都道府県の補助列は、網羅的な正解表による定量採点をしていない。このため主指標は「採点した必要項目の取得率」であり、「画像全体を正しく読み取る率」ではない。科目・得点・満点・全国偏差値とCの単元別結果から初期の復習案を作る、という限定目的の予備比較としては有効だが、AIが補助列を計画の根拠に使った場合、その根拠まで正確だったとは保証できない。計画に用いる列を構造化して限定するか、用いる列を追加で正解表に含める必要がある。元の採点基準を事後に変えて今回のスコアを上書きしない。

志望校別のA/B判定を画像から除いたことは今回の比較の支障ではない。日々の復習・定着を目的にするなら必須ではなく、志望校に特化した受験計画まで扱う場合は、本人が確認した目標校、受験科目・配点、試験日等を別に扱う。判定だけから本人の希望を推定しない。志望校別評価欄の読取性能は今回未評価。

Flashの51項目の失点は、1画像のJSON打ち切り30項目と、別の1画像の全国平均点を％とした21項目に集中している。88.7%を「数字の11.3%がランダムに誤読された」と解釈しない。一方、点と％の取り違えは計画に影響するため、単なる表記の問題として除外しない。

miniの6.9%は、450項目中、正確31・誤り46・欠落358・対応不明15という内訳。短い要約にして必要行を省いたことが主因だが、回答した数値にも実際の誤りがある。画像細字・入力の扱い・抽出と提案を一度に求める設計・経路の影響は未切り分けであり、モデル一般のOCR能力が6.9%だとは結論しない。OrcaReplay送信時の画像保持は確認済みだが、OrcaReplayを外した直接呼び出しや表の切り出しによる対照試験は未実施。

運用の合否を単一の「95%／99%」で決めない。重要科目の得点や平均点の1件の取り違えが学習の優先順位を変え得るため、重要項目の誤反映、検知できた不明値、処理失敗、計画の優先順位の妥当性を別々に評価する。まず今回の資料で重要項目の未検知の誤りをなくすことを改善目標とし、不明な値を計画の確定根拠に使わない。その上で未使用の模試でも確認し、人による確認が必要な割合と総費用を測る。数値をすべて正しく読めても学習計画の教育的妥当性は別評価が必要。

次の改善試験は、(1) 科目・設問ごとの構造化抽出だけを行う、(2) 得点率・平均との差をコードで計算して検証する、(3) 確認された数値から計画を作る、という分離を優先する。小さい文字には表ごとの切り出しも比較する。これは改善案であり、改善後の精度を測定済みという意味ではない。公式資料も日本語等の非ラテン文字、小さい文字、画像のリサイズを注意点に挙げ、用途に沿った評価と人の判断の併用を推奨している（[画像入力の制約](https://developers.openai.com/api/docs/guides/images-vision#limitations)、[評価設計](https://developers.openai.com/api/docs/guides/evaluation-best-practices)）。

## 推奨する使い分け

1. **現在の模試読取・プロフィール提案はFlashを第一候補にする。** 必要項目全体の取得と単元への紐付けが優れていた。ただし、現行の15秒制限のまま採用完了としない。
2. **低コスト化はFlash-Liteを候補に残す。** 構造化した抽出結果を機械検証し、欠落・単位不明・整合性不良の時だけFlashへ再読取を依頼する案を、別試験で評価する。この切替方式の成功率・総費用はまだ測っていない。
3. **模試読取の代替先にminiをそのまま使わない。** 複雑な表で科目・行・列の対応が崩れた。Google系障害時の別プロバイダー候補は別途比較し、未検証のモデルを安全な代替と断言しない。当面は失敗状態を保持して再試行・手入力につなぐ方針を検討する。
4. **会話モデルの選定は今回の結果からは変更しない。** 自己紹介や生徒との対話、授業資料全般はこの試験の対象外。

先生には原画像を毎回すべて再入力させず、AIが抽出・検算・計画案作成まで進め、疑義のある箇所と根拠を示して承認してもらう。これは本サービスの「先生は授業記録等を渡し、AIの課題・計画を確認して承認する」という方針と整合する。

## 費用・実行条件・OrcaReplay

- 確認できたAPI費用: **$0.201082**（主比較$0.142690、追加12回$0.058392）。課金応答を得られなかった15秒タイムアウト1回は含まない。
- 未確定1回について$0.25を留保した予算管理額: **$0.451082**。これは請求額ではない。最終請求額の確定には管理画面で当該タイムアウト分の照合が必要。
- 承認上限: **$2**。呼び出し前に1回$0.25を確保し、不明費用をゼロにしないガードを使用。実験用キーのみ使用し、サービス本体のキー・DBを変更していない。
- モデル要求名: `google/gemini-2.5-flash`、`google/gemini-2.5-flash-lite`、`openai/gpt-4o-mini`。応答の実使用名はそれぞれ `gemini-2.5-flash`、`gemini-2.5-flash-lite`、`gpt-4o-mini-2024-07-18`。他モデルへのアプリのフォールバックは無効。
- アプリと同一の画像変換関数をChromeで実行。長辺1600px以下、JPEG品質0.85、PDFの描画倍率は最大2倍。模試解析のsystem prompt、Zod JSON Schema、`max_tokens=6000` を同じにした。temperatureなどはアプリ同様未指定。
- Bの元PNG2枚は15MiB超過のため受付不可。原本を変えず同解像度のJPEG品質98へ変換してから通常の前処理に渡した。B写真の比較はこの派生JPEGによる。
- 精度比較は全モデル60秒期限。最初の15秒試行だけ別扱いの失敗として保持。主比較で15秒以内だった回数はFlash 1/9、Lite 6/9、mini 9/9。アプリには現在1試行15秒・全体45秒の制限と修復・代替処理があり、この試験はそれら込みの本番成功率ではない。
- OrcaReplay **0.4.0** の `record generic-openai` と `compare --from 1 --models ...` でライブ比較。各比較forkは再生0回・実API呼び出し1回。オフライン再生を新しい試行として数えていない。
- ワーカーは毎回元の正規化画像を読み込む。実プロキシ＋ローカル上流スタブで、3モデルともモデル名以外の送信JSONが完全一致することを検証した。
- トレース保存時、画像base64の一部が高エントロピー情報としてマスクされる。送信画像自体は変更されないが、保存トレースだけで画像を復元する方式には使わない。元画像ハッシュ・要求JSONは別に保持した。
- OrcaReplayのCLIの `pass` はワーカー正常終了であり、正確さを意味しない。CLI推定費用が空だったため、費用はOrcaRouterの `usage.cost_usd` を採用した。
- 実行順は各入力についてLite→Flash→miniで固定。同時並行実行なし。順序効果・負荷・キャッシュを分離する実験ではない。

## この実測から言えること

実物2回分・3ページの模試を9つの入力条件にし、OrcaReplayで同じ入力・スキーマのまま3モデルを比較した。
必要項目を意味まで正しく取れた割合、形式エラー、時間、費用を別々に評価している。
Flashは情報全体の取得に優れ、Liteは単科目・設問の基礎数値を低コストで読めた。
一方で、平均点と割合の混同や、推論枠によるJSON切れも見つかっている。
モデル名だけで選ばず、機械検証と人の承認をどこに置くかまで実測に基づいて決める。

- **費用対効果:** 単なる最安比較ではなく、取り出せる情報・失敗・費用を併記。安いモデルからの条件付き再読取は次の検証課題と明示する。
- **信頼性・堅牢性:** タイムアウト・出力上限・誤った成功を実例で説明し、失敗を隠さない。プロバイダー停止を想定した切替試験は未実施。
- **自律性:** 抽出、計算、検証、計画案作成をAIとコードが担当し、人には疑義と承認事項を示す改善につなげる。今回その改善を実装済みとは言わない。
- **セキュリティ:** 個人情報の転記禁止・資料内指示をデータとして扱う現行プロンプト、検証関数、実験キーの分離を継承。ただし攻撃入り画像によるプロンプトインジェクション耐性試験は未実施で、防御効果をこの結果から主張しない。
- **位置づけ:** 模試から課題を作るだけでなく、説明対話・理解度把握・復習計画の循環へ、根拠のある初期情報を渡すための入口にあたる。

少数の書式・同一ページの条件違いによる予備評価。低学年向けの資料、手書き、極端な反射・ぼけ、多ページ、異なる模試会社全般への一般化は未検証。C_shadowはページ下部の補足が他条件と同じ範囲ではないため、主評価は共通して写っている設問表に限定した。予算を使い切るための追加試験や、架空PDFとの混合集計はしていない。

- `benchmark-data/exams/normalized/manifest.json`: 入力・変換関数ハッシュ等

- `benchmark-data/exams/runs/field-scores.csv`: 項目ごとの期待値・取得値・判定
- `benchmark-data/exams/runs/summary.csv`: 入力×モデルごとの精度・費用・時間
- `benchmark-data/exams/runs/scores.json`: 採点理由・回答ハッシュ

- `benchmark-data/exams/work/.orca/runs/`: OrcaReplayの実行記録
- `benchmark-data/exams/runs/environment.json`: コード版・実行条件
