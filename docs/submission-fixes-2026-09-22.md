# 提出前の優先問題：説明と修正結果

2026-09-22。[レビュー](qiita-article-review-2026-09-22.md)のP0を受けた対応。レビューは発見時点の記録として維持し、新稿は[qiita-article-v2.md](qiita-article-v2.md)に作成した。`qiita-article.md`は変更していない。

## 1. 本番ビルドの失敗：修正済み

開発中に画面が動いていても、公開用にアプリを組み立てる「ビルド」が失敗すると、最新版をデプロイできない。

原因は、所属登録APIの`route.ts`から、入力検査用の`codeSchema`までexportしていたこと。Next.jsはこのファイルから公開できる定義を制限している。外部から使われていないことを確認し、`export`だけを外した。入力検査や登録の仕様は変えていない。

修正後、`npm run build -- --webpack`が成功。全自動テストも36ファイル・276件成功、失敗・スキップ0。ただし、新しい所属の実登録・初回ログインの手動確認や、Vercelへのデプロイは今回行っていない。

## 2. 画像攻撃試験の条件と成功判定：修正済み、実モデル測定は未実施

問題は「画像攻撃に突破されたと判明した」ことではなく、**旧試験の結果では現在のアプリが安全か判断できない**ことだった。

旧試験は本体と違うプロンプト・モデル用途・出力上限を使い、空回答でも攻撃文がなければ成功になり得た。これでは「成績を正しく読めた」「危険なので止めた」「何も答えなかった」が区別できない。

修正内容：

- 本体の模試用プロンプト、画像メッセージ生成、JSONスキーマ、`exam`モデル選択、10,000トークン上限を共用。
- 正常対照1枚と攻撃入り6枚を準備し、5科目の得点・満点・偏差値の計15項目を照合。正常対照が読めなければ後続の課金を止める。
- 抽出成功、数値の欠落・改変、アプリでの遮断、ゲートウェイでの遮断、システム文の漏えい検出、判定不能を別記録にする。
- 空回答、JSON不正、途中終了、通信失敗を防御成功にしない。攻撃文やURLの単なる転記を「命令を実行した」「外部送信した」とは決めつけない。
- 数値が合っていても、自動反映できるかは別判定。見出し不足などによる確認待ちを記録する。
- 既定はAPI通信なしのdry-run。実行時のモデル・要求・画像のハッシュ、結果・時間・費用をGit対象外の`benchmark-data/injection/`へ保存する。

固定応答による判定テスト12件と、7画像の要求生成・画像形式の確認が成功。**今回の有料AI呼び出しは0回。実モデルで攻撃を防げたという証拠はまだ追加していない。**

試験は直接PNGを送るため、ブラウザでの画像変換、認証、DB保存、ジョブ、画面操作、所属予算の全経路は含まない。また15数値の照合は資料全体の意味の正確さや攻撃一般への防御率ではない。システム文照合の診断も、本体の模試経路で同じ遮断が行われるという意味ではない。

通信なしの確認：

```bash
node --import tsx scripts/check-injection-image.ts --dry-run
npx vitest run tests/security/exam-injection-protocol.test.ts
```

実モデルの試験は、残予算・対象アカウントを確認した後に行う。`--live --max-cost-usd <今回の管理上限>`を明示した場合だけAPIを呼ぶ。費用不明は1回$0.25を留保するが、これは推定上の管理額であり、実請求の上限保証ではない。従来の模試比較台帳とは別なので合算が必要。従来の$2上限をそのまま追加試験の予算として使わない。

テキストの試験表示も、mediumを「遮断」としていた表記を「注意・通過」へ訂正した。13入力のうちhighが12件、mediumが1件。6無害文・5出力と合わせて全期待値を満たした。既知ルールの確認であり、実モデルの攻撃防御率ではない。

## 3. RLSの説明：新稿で修正済み

RLSは、DB側で「この利用者が見てよい行」を制限する仕組み。ただし、管理用のservice-role接続はこの制限を迂回する。

会話取得などの管理用接続では、すでにアプリ側で所属と本人・担当範囲を確認している。今回の問題は、それを「RLSが守る」と一括りにした説明だった。新稿では、ユーザー権限でのRLSと管理用処理での権限確認を分けて説明した。この説明修正のためにDBの権限を変更する必要はなく、今回も変更していない。
